## 1. 建议的重构边界

建议重写太空渲染底座：将目前围绕天空壳、手工排序和分散 RenderSystem 状态操作的实现，迁移为具有独立天体深度、线性颜色和明确资源生命周期的场景渲染管线。

保留并复用以下成果：

- `UniversePosition`、宇宙注册表、服务端同步和数据包定义。
- 航行控制、停靠点、航线、跃迁阶段及已确认的航行节奏。
- `SpaceRenderContext` 的帧快照概念、候选星系查询及 LOD 滞回思想。
- 已有贴图、材质遮罩、云层贴图和 shader 注册入口。
- 当前客户端的可选模组边界与降级能力。

替换范围包括：天空壳投影策略、天体遮挡、表面光照、大气合成、近景恒星和 GPU 资源组织。旧视觉参数先经过适配层转换，避免架构迁移同时改变所有已确认画面。

## 2. 当前实现的限制

以下区分代码可确认的事实与由此推断的扩展限制；不把静态审查当作实机故障复现。

| 代码证据 | 当前行为 | 改造理由 |
| --- | --- | --- |
| `PlanetRenderer.java:303` | 远行星中心和半径一起缩放至距离 280 的天空壳；表面关闭深度写入 | 单个球体的半径/距离比例得到保留，但不能直接获得统一的真实天体深度；中心排序无法处理所有交叠情况 |
| `SpaceRenderer.java:75` | 先绘制恒星，再绘制全部行星 | 行星会按类别覆盖恒星，尚未由每像素真实距离决定遮挡 |
| `RingRenderer.java:103` | 依据环段中心距离分成前后两次绘制 | 是现有遮挡策略的补偿逻辑；引入一致的天体深度后可以简化，但透明环仍须处理透射 |
| `planet_surface.fsh:81` | 用 smoothstep 区分昼夜，大片昼面趋于相同光照；高光和发光贡献被限制 | 体积感与材质响应仍受美术颜色混合支配，缺少统一的入射光、反射和曝光关系 |
| `PlanetRenderer.java:338` / `atmosphere.fsh` | 大气先于表面绘制；按壳体弦长计算加色亮边 | 实心盘内的地表不会自然经过大气透射和散射合成；密度高度变化、观察方向和太阳遮蔽需要更完整模型 |
| `StellarRenderer.java:165` | FULL 恒星仍由圆盘、glow、射线和粒子层组成 | 近景缺少由球面法线、表面结构和自转形成的球体感 |
| `PlanetRenderer.java:146` | REDUCED 和 FULL 表面都使用 64×128 球体 | 当前 LOD 主要节省附加效果，尚未明显降低球面几何成本；每张球面提交 32,768 个顶点 |
| `SpaceBackgroundRenderer.java:182` | 内置 2,000 星点每帧在 CPU 旋转、计算闪烁并上传顶点；时间来自系统时钟 | 星空后端不可用或性能档时仍有这条路径；截图回放和暂停行为也不统一 |
| `SpaceRenderPassState.java:12` | 把状态恢复为一组默认值 | 不能等价于恢复进入渲染时的调用方状态；新增 framebuffer、viewport 等状态后更需明确边界 |
| `CloudShellRenderer` / `AtmosphereShellRenderer` | 网格分开生成；上传失败标志没有恢复入口 | 缺少统一的几何复用和重建机制；需区分 shader 的引擎所有权与模组 VBO/FBO 的所有权 |
| `SpaceVisualQuality.java` | HIGH 和 ULTRA 当前返回相同能力开关 | 画质档位还没有对应不同的采样量、网格精度或缓冲分辨率 |

### 一个应先校正的数学约定

`CelestialLodPolicy.angularDiameterDegrees` 使用 `2 * atan2(radius, distance)`。

若 distance 表示观察点到球心的距离，且观察点位于球外，球体轮廓角径应为：

```text
angularDiameter = 2 * asin(radius / distance)
```

例如 distance = 2 × radius 时，球体角径为 60°，当前计算约为 53.13°。远距离差异很小，近距离不能忽略。

改造时需明确球外、贴近表面和球内的处理。LOD 最终应使用角径换算后的屏幕像素直径，同时计入垂直 FOV 与 viewport 高度；仅修公式仍不足以支持不同分辨率的质量预算。

## 3. 目标管线

从固定、显式的 Pass 列表开始，不必先开发通用渲染图框架。

```text
宇宙目录 + 航行状态 + Minecraft 相机
              ↓
SceneBuilder：相对坐标、姿态、可见性、灯光、LOD、效果预算
              ↓
天空色场 / 远景星点
              ↓
行星与恒星的不透明表面：写独立天体深度
              ↓
云、光环、大气、日冕：读取深度，组合透射与辐射
              ↓
跃迁视觉：按现有航行阶段组合
              ↓
受控 Bloom + 色调映射
              ↓
在 Minecraft 天空阶段合成颜色
              ↓
Minecraft 船体、玻璃、实体、HUD
```

建议的职责划分：

| 组件 | 职责 |
| --- | --- |
| `SpaceSceneBuilder` | 统一产生可见天体与灯光数据；绘制代码不再反复查询游戏状态 |
| `SpaceView` | 宇宙到观察空间的变换、相机/FOV、投影和深度编码约定 |
| `CompiledBodyVisual` | 在目录更新时解析资源 ID、材质参数和默认值，避免每帧重复解析 |
| `SpaceRenderResources` | 管理模组拥有的 VBO、FBO、LUT 和临时目标；处理 resize、失效、重建和释放 |
| `SpaceRenderPipeline` | 决定 Pass 顺序、质量预算与降级；控制对 Minecraft 的状态修改边界 |
| 各专项 Pass | 消费已准备好的场景数据，只负责绘制 |
| `SpaceDebugCapture` | 固定时刻回放、截图、CPU/GPU 分段计时和资源统计 |

帧数据可以使用复用数组和只读视图，不要求每帧创建大量不可变对象。shader 仍经 Minecraft/NeoForge 的注册生命周期管理，避免资源管理器重复释放由引擎拥有的 shader。

## 4. 首要改造：统一投影与遮挡

### 4.1 使用独立天体深度

太空颜色和天体深度进入独立 framebuffer，最后只向 Minecraft 天空阶段合成颜色。压缩后的宇宙深度不写入 Minecraft 主深度，避免干扰船体与实体。

不透明行星和恒星共用深度约定，按片元交点距离决定遮挡。远景背景星点视作无穷远；有位置的恒星、行星和中继站则是场景对象。

这为以下画面提供共同基础：

- 行星从恒星前方经过，恒星圆面与日冕分别被遮挡。
- 卫星与主星交叠时，遮挡不依赖类别和中心排序。
- 光环远侧被球体遮挡，近侧对球体产生透射与阴影。
- 后续中继站、小行星等对象加入相同场景。

独立 framebuffer 本身不解决远距离精度。第一阶段应比较独立投影下的普通深度、距离分层及对数距离编码；所有天体和相关透明效果必须采用同一约定。

如果保留每个球体的局部天空压缩，须从局部坐标重建对应宇宙距离，再写一致深度，不能把局部壳体深度直接当作真实深度。

### 4.2 采用混合表示

近景使用共享球体网格；中远景可使用解析球体 impostor：在屏幕包围区域内求射线与球体交点，得到 UV、法线和距离；极远景使用星点。

解析球体与逐步 ray marching 不同，不需要沿射线搜索整个空间。是否用它替换大面积近景网格应经过测量：写 `gl_FragDepth` 会影响早期深度测试优化，屏幕覆盖大的物体不一定更快。参见 [Khronos 的早期片元测试说明](https://www.khronos.org/opengl/wiki/Force_Early_Depth)。

透明层仍需单独设计。最初限定少量可见壳体，使用深度裁剪和有序组合；多层大气/光环交叠是专项验收项，不能假设开启 depth test 就会自动正确。

### 4.3 相机坐标与美术尺度

保留已有宇宙相对坐标和稳定姿态变换。后续可加入观察者相对飞船参考点的位置，让近处空间设备呈现小幅视差。

玩家在船内移动的 Minecraft 距离如何换算为宇宙距离，需要显式比例；不能直接把方块坐标相加到当前宇宙坐标。

`StellarDistanceResponse` 明确属于美术距离曲线。新系统可继续接受这些参数，但应把真实位置、几何/视觉半径和曝光响应分开，不让美术缩放隐式改变航线几何。

## 5. 第二个基础：线性光照与 HDR

建议太空场景使用线性颜色，优先验证 RGBA16F 颜色目标，完成局部曝光和色调映射后合成到主画面。HDR 指内部渲染范围，不要求 HDR 显示器。

明确所有资源的色彩语义：albedo 按颜色纹理解码；roughness、遮罩、法线和高度属于数据，不能套同一颜色转换。输出到 Minecraft 时核对实际目标编码和现有 shader 管线，防止重复 gamma 转换。相关颜色与材质约定可参考 [Filament 官方文档](https://github.com/google/filament/blob/main/docs/Filament.md.html)。

这样恒星、熔岩、海洋高光和大气可以共享亮度关系，减少当前 shader 中为 LDR 输出加入的局部截断。

实施建议：

- 初期使用固定、可调曝光；稳定后再评估有上下限的缓慢曝光变化。
- Bloom 仅作用于太空内部结果，优先低分辨率多级模糊；地表漫反射与薄大气不应普遍发光。
- 近景表面保持全分辨率；大气、日冕与 Bloom 可按预算降低分辨率，并采用能保护轮廓的上采样。
- 本地检查浮点目标的完整性与能力，支持明确降级。

成本必须记录：1080p 的一个 RGBA16F 颜色目标加一个按 4 字节估算的深度目标，基础存储约 24 MiB；4K 约 95 MiB。这里尚未包括 ping-pong、Bloom、LUT、驱动开销和已有贴图。不要为未来需求预先增加多套全分辨率 G-buffer。

## 6. 视觉升级建议

### 6.1 行星：从昼夜颜色混合走向统一材质

直接光照以入射光和 `max(N·L, 0)` 为基础，保留可控的环境光与美术夜面下限。海洋采用粗糙度、Fresnel 和一致的高光模型；岩石和冰使用各自参数，熔岩由独立 emissive 项贡献。

允许逐步引入 GGX、法线/高度贴图和材质类型，但先验证昼面梯度与海洋高光是否已经明显改善。现有 R/G 遮罩先保持兼容，新增材质布局应版本化或使用明确的新字段。

统一灯光数据后，为可见天体加入解析遮挡：沿太阳方向检测少量球体/环，支持行星投影到光环、卫星食和地表阴影。云影继续使用已有球壳投射方式，纳入相同光照组合。

多光源先限制为主光源加至多一个有实际影响的次光源，避免每个片元扫描全部恒星。

### 6.2 大气：优先升级为透射和单次散射

建议第一版从少量样本的 Rayleigh/Mie 单次散射开始，加入随高度变化的密度、太阳相函数和行星对太阳光的遮挡。合成遵循：

```text
C_out = L_scatter + T_view * C_behind
```

`C_behind` 包括行星地表、云层或更远背景；大气积分在可见实体交点处终止。这个改变同时影响亮边、盘内空气感和背光表现。

后续用 transmittance 等 LUT 降低重复积分成本；参数相同的天体共享预计算结果。屏幕效果若读取已有场景颜色，应使用独立读写目标，避免 framebuffer 反馈。

参考 [Hillaire 的大气渲染论文配套实现](https://github.com/sebh/UnrealEngineSkyAtmosphere)，其源码包含不同 LUT 的生成。本文建议的是根据本项目观察距离与预算裁剪后的方案，不直接移植完整引擎系统。

低档可保留便宜壳体近似，高档提高采样/查表质量。视点进入大气后的行为必须单独验证，不能只以远景亮边作为完成标准。

### 6.3 恒星：优先做光球表面

FULL 恒星建议具备球面法线、缓慢自转、临边昏暗，以及固定在天体空间中的颗粒和黑子。近景用球体，中景可用解析球体；两者共享表面模型。

日冕与光球分开：日冕由少量低频结构和受控外层形成，耀斑作为有预算的局部结构。温度或美术色彩参数决定基色，亮度进入统一 HDR 管线。

第一阶段先验收有体积感的光球和遮挡，再增加复杂日冕。旧圆盘实现可作为中低档降级路径。

### 6.4 云层与气态巨行星

近期保留二维云壳和现有云影。可从同一云密度数据得到轻微明暗厚度变化，再评估两层不同漂移的壳体；层数和屏幕填充率必须计入预算。

气态巨行星优先增加可控的纬向差速、云带扰动和局部风暴。纹理主体保留，程序化变化只改变少量细节，避免高频噪声吞没球体形态。

体积云留给近距离高档实验；不作为全部行星的默认实现。

### 6.5 深空与星点

将背景色场改为按观察方向求值的全屏 shader 或静态天空资源，避免几何尺寸 430 与 Minecraft far plane 耦合。

方向场中加入很淡的银河尘带、疏密变化和小范围暗尘遮蔽。颜色通过已有星系环境权重连续混合；方向场固定在宇宙中，保持旋转稳定。

StellarView 继续作为可选背景星空后端；内置后端也升级为静态 VBO + shader 变换。首版可使用预展开顶点，不强制依赖 instancing 或 compute shader；能力允许时再启用批量实例化。

后端接口需约定输出颜色空间、亮度、目标 framebuffer 和状态恢复；把现有 StellarView 绘制直接移入 HDR 目标，不等价于已经完成颜色适配。

背景星点与具有真实位置的恒星应各自有明确职责；前者提供远景层次，后者参与遮挡和导航。

统一时间输入，去除星点的系统时钟依赖。共享时钟保留高精度，周期动画在提交 uniform 前归一化，避免长期游戏时间转换为 float 后失去细小时间变化。

### 6.6 跃迁

保留已经确认的航行阶段和视觉节奏，逐步把逐帧 CPU 构建的线条/粒子转为静态模板加 shader 时间变换。

星点汇聚、天体可见性、隧道和抵达效果共用阶段参数。跃迁仍可以采用美术化尺度，但需要明确哪些 Pass 参与天体深度、哪些属于有意覆盖的视觉层。

## 7. LOD、质量与资源管理

### 7.1 真正减少工作量的 LOD

将质量选择拆为：几何精度、表面材质复杂度、透明效果采样、屏幕目标分辨率和可见效果数量。

- 共享少量球体网格，依据像素误差和滞回选择；不再让所有可见球面使用相同细分。
- 表面、大气、云层可共享标准球体格式；中远景允许使用不同表示。
- 几何转换优先使用误差阈值和滞回，材质/光晕可以渐变。不透明表面的 LOD 过渡不能简单叠加两个半透明球体，否则会出现亮度和遮挡问题。
- 对近景高成本恒星、大气和日冕设总预算，保留目的地的重要性。
- 视锥判断使用天体角范围/屏幕包围区域，不能直接拿宇宙绝对坐标套 Minecraft 的方块视锥。

### 7.2 HIGH 与 ULTRA 应有实际差别

| 档位 | 建议的可见差异 |
| --- | --- |
| Performance | 内置 GPU 星点、简化表面、便宜大气；低透明效果预算 |
| Balanced | 统一深度和光照；云壳；大气受限采样或查表；关闭昂贵附加效果 |
| High | 更完整的云影/食影；较高大气质量；受控 Bloom 和光球细节 |
| Ultra | 增加近景采样与细节预算；实验性云层/日冕质量；明确更高成本 |
| Custom | 独立功能开关和采样预算，并显示所用配置 |

具体采样数在测量后定，不用功能开关数量替代实际帧成本。

### 7.3 生命周期与状态边界

- 模组 VBO/FBO/LUT 明确所有者；shader 遵循引擎注册与释放机制。
- 在 resize、资源重载、宇宙目录变化和会话切换时分别失效对应资源，不要求无关静态网格全部重建。
- 资源上传失败应允许在明确的重建事件后重试；避免永久失败标志只能靠重启恢复。
- 在太空渲染入口保存并恢复被修改的 framebuffer、viewport、投影、shader、纹理和相关混合/深度等状态。内部 Pass 使用明确状态描述，避免每个 draw 通过大量 GL 查询保存状态。
- uniform 引用、解析后的资源 ID 和材质包随资源代次失效。

## 8. 实施顺序与验收门槛

每一阶段都保留可比较的运行结果。基础迁移期间用开发选项切换旧/新路径，验收后移除重复实现。

| 阶段 | 交付内容 | 进入下一阶段的依据 |
| --- | --- | --- |
| A：测量与回放 | 固定场景/时刻捕获；CPU/GPU 分段计时；draw、上传、资源统计 | 有可重复基线，确认哪些成本值得优化 |
| B：坐标和帧数据 | `SpaceView`、场景准备、资源 ID 编译、统一时钟；校正角径与像素 LOD | 当前姿态、FOV、角尺寸和航行画面有行为测试与截图对照 |
| C：深度管线 | 独立目标、统一天体深度、正确交叠；迁移表面和光环 | 行星/恒星/卫星遮挡、环边缘、舷窗和玻璃通过专项验证 |
| D：颜色与材质 | 线性输入、HDR、固定曝光、表面光照、选择性 Bloom | 颜色编码正确；海洋、冰、岩石、熔岩各有清晰响应；夜面可读 |
| E：大气 | 透射 + 单次散射，再评估 LUT | 白昼、终止线、背光和近大气视角均连续，没有轮廓接缝 |
| F：恒星与环境 | 立体光球、有限日冕、背景方向场、内置 GPU 星空 | 各 LOD 外观衔接；恒星遮挡与亮度稳定；两种星空后端有明确边界 |
| G：预算与清理 | 高低档差异、重建机制、移除旧重复逻辑 | 自动检查、客户端矩阵、资源生命周期和性能均有记录 |

B/C 是最值得先投入的基础；D/E/F 的视觉收益建立在这些约定上。

### 验证重点

- 数学测试：球体角径、屏幕包围范围、坐标姿态、球/环相交、深度编码的单调性与精度。
- 固定场景：Lush 昼面/终止线/夜面、Barren、Frozen、Molten、Gas Giant 环正侧视、Rocky Moon，以及行星遮星和卫星交叠。
- 航行：短航线、跨星系出发、中段、抵达；当前角尺寸和阶段节奏作为回归基线。
- 集成：不同 FOV、窗口比例、低视距、第一/第三人称、行走摇晃、玻璃、资源重载、resize、退出重进及不同宇宙数据包。
- 可选依赖：StellarView 存在、缺失、关闭及失败回退；有实际目标组合时再验证 Iris 等其他渲染模组，不把未经测试的兼容性写为已支持。
- 性能：分别记录 CPU 与 GPU；GPU 查询异步读取，避免为了测量引入每帧同步等待。记录 P50/P95、分辨率、硬件、驱动和目标内存。

初始优化约束建议是：普通停靠时不因动画重建/上传静态天体网格；新增高档效果必须能单独计时和关闭。最终毫秒预算需在实际验收机器上确定，本文没有已测出的性能承诺。

## 9. 应保持为后续实验的方向

黑洞/引力透镜可通过预留的场景颜色和天体距离接口扩展；全屏深度图、通用延迟渲染、全场景体积云、全局 TAA 和完全模拟恒星等方向，需要独立收益与成本证据。

当前最有价值的结果是：天体遮挡一致，行星光照有体积感，大气真正影响观察路径，近景恒星有光球表面，且不同画质档位具有可测量的成本差别。
