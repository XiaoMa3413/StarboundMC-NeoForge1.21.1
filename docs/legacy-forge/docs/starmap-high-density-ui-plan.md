# 星图高密度 UI 渐进式重构计划

> 状态：HD-0～HD-5 已完成并通过实机验收
> 编写日期：2026-08-22  
> 完成日期：2026-08-23
> 基线分支：`feature/starmap-ui-rework`  
> 基线提交：`a7daa0f`  
> 目标版本：Minecraft 1.20.1 Forge

## 1. 为什么需要独立计划

Minecraft 的 `Screen` 使用“GUI 逻辑像素”，而不是直接使用显示器物理像素。
GUI Scale 越大，屏幕提供给界面的逻辑宽高越小。现有星图虽然接近全屏，面板、
文字和按钮仍然只能落在较粗的整数坐标网格上，因此继续增加二级菜单和小型信息
组件会出现线条粗、间距拥挤、图标细节不足等问题。

当前星图场景本身已经绕开了一部分限制：`StarMapCanvas` 会生成高分辨率动态纹理，
天体也有总览/聚焦两级像素贴图。然而屏幕框架、详情面板、按钮、文字和部分动态
覆盖层仍由 `GuiGraphics` 在普通逻辑坐标中直接绘制。下一步应先建立高密度 UI
基础层，再考虑更复杂的详情菜单。

## 2. 本计划的目标与非目标

### 目标

- 在 GUI Scale 较大时，让星图利用更多物理屏幕像素。
- 保持现有近全屏响应式布局、紧凑抽屉和三级导航行为。
- 为边框、细线、图标、状态标记和未来信息卡提供 2× 设计精度。
- 保留中文显示、键盘导航、旁白和现有按钮行为。
- 每个模块都能独立提交、回退和实机验证。
- 避免因高清化而持续增加每帧纹理生成或明显提高显存占用。

### 非目标

- 本计划不立即实现 Starbound 风格二级详情菜单。
- 不在同一轮重新设计颜色、信息结构或交互逻辑。
- 不修改星系数据、跃迁规则、页面层级或天体坐标。
- 不强制玩家修改全局 GUI Scale。
- 不承诺在 GUI Scale 1 下凭空产生超过显示器物理分辨率的细节。

## 3. 现有实现审计

### 可以直接保留

| 模块 | 原因 |
|---|---|
| `StarmapPage` | `GALAXY / SYSTEM / BODY_FOCUS` 页面状态已经明确。 |
| `StarSystems`、`PlanetEntry`、`StarmapBodyVisual` | 导航数据和视觉资源已数据化。 |
| `StarmapGeometry`、`StarmapFocusGeometry` | 总览与聚焦几何有纯逻辑测试。 |
| `StarmapViewport` | 已集中处理创作画布和界面坐标投影，可继续扩展。 |
| `StarMapCanvas` | 已是高分辨率动态纹理，应作为高密度场景层保留。 |
| 三级导航、抽屉、跃迁同步 | 已经过多轮实机验证，不应随视觉基础改造重写。 |

### 需要渐进式重构

| 现状 | 问题 | 处理方向 |
|---|---|---|
| `ShipConsoleScreen` 约 1900 行 | 状态、绘制、排版、动画和控件高度耦合 | 只抽离渲染职责，不先迁移业务状态。 |
| `StarmapLayout` 只输出整数逻辑坐标 | 无法表达半个逻辑像素的细线和间距 | 保留布局算法，新增高密度坐标适配层。 |
| `SciFiButton` 直接用整数 `fill` 绘制 | 高 GUI Scale 下边框粗糙 | 保留 `Button` 的输入/旁白，替换其视觉绘制层。 |
| 详情面板直接在 Screen 内排版 | 后续二级信息会继续扩大单类 | 高清基础稳定后抽取独立详情渲染器。 |
| 文字使用 Minecraft 默认字体 | 单纯提高坐标密度不会提高字形分辨率 | 第一阶段保持不变，单独做字体可行性门槛测试。 |

### 暂时不碰

- 页面记忆与聚焦主体/选中卫星恢复。
- 跃迁期间的自动切页、飞船动画和进度条。
- 天体像素贴图及锁定占位规则。
- 服务端网络包和燃料逻辑。

## 4. 三种实施范围比较

| 方案 | 内容 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 只高清化星图背景 | 继续扩展 `StarMapCanvas`，其他 UI 不变 | 风险最低 | 详情卡、按钮和文字仍受低逻辑分辨率限制 | 不足以支撑精细 UI |
| B. 渐进式 2× 混合层 | 场景纹理保留；边框、图标和按钮外观使用 2× 虚拟坐标；文字先保持原生 | 改善明显、风险可控、可逐步迁移 | 会短期存在高清视觉与原生文字混合 | **推荐** |
| C. 整屏离屏渲染并重写输入 | 整个 UI 在独立高分辨率 RenderTarget 中绘制，所有控件自定义 | 理论自由度最高 | 投影、裁剪、输入、旁白、字体、资源重载都需重写 | 当前不采用 |

## 5. 推荐架构：2× 虚拟坐标，而非整屏重写

推荐先实现一个轻量的 `StarmapUiDensity`：

- 当前布局仍以 Minecraft 逻辑坐标计算，避免破坏响应式行为。
- 渲染装饰层时，将坐标乘以密度 `D`，同时把绘制矩阵缩放为 `1 / D`。
- `D=2` 时可以表达 `0.5` 个普通逻辑像素的边线和间距。
- 按钮的真实点击框继续使用原有逻辑坐标，所以第一阶段无需重写输入。
- 鼠标坐标只在未来完全虚拟化的组件内部才转换。

示例：普通坐标中的 `x=20.5` 无法直接交给大多数整数绘制 API；高密度层会在
2× 坐标中绘制 `x=41`，再整体缩小一半，最终落在显示器更细的像素位置。

### 密度选择

推荐规则：

- GUI Scale 1：`D=1`，因为没有额外物理像素可用。
- GUI Scale ≥2：优先 `D=2`。
- 若窗口过小、纹理尺寸超限或兼容性检查失败：自动回退 `D=1`。
- 第一版不开放玩家设置项，避免尚未稳定时扩大测试组合。

### 为什么第一版不需要整屏 RenderTarget

矩阵缩放已经能让线条和几何使用子逻辑像素，并直接由 GPU 映射到物理像素。
现有 `StarMapCanvas` 本身已负责最复杂的高分辨率场景纹理。额外建立全屏
RenderTarget 会引入纹理生命周期、窗口缩放、裁剪和显存管理问题，收益暂时不足。
只有后续确实需要整屏滤镜、遮罩或复杂合成时，才重新评估离屏渲染。

## 6. 分阶段实施

### HD-0：密度数学与对比原型

新增建议模块：

- `StarmapUiDensity`：密度选择、逻辑/虚拟坐标转换。
- `StarmapHiDpiGraphics`：受控的矩阵进入/退出、细线与矩形绘制。
- 对应纯逻辑单元测试。

界面只增加一个可临时开启的对比样片：同一区域显示普通 1 px 边框和高密度
0.5 px 边框，不迁移正式 UI。

验收：

- GUI Scale 2、3、4 下能直观看出线条密度差异。
- 对比样片不影响鼠标和页面状态。
- 窗口/GUI Scale 改变后密度重新计算。

提交边界：只提交密度工具、测试和临时验证开关；未通过视觉验证即可整块撤销。

### HD-1：静态框架高清化

抽取 `StarmapChromeRenderer`，迁移：

- 全屏背景渐变。
- 主面板双层边框和角标。
- 星图画布边框。
- 详情面板背景。
- 燃料条边框与填充。

不迁移文字、按钮、天体交互和飞船动画。

验收：

- 各 GUI Scale 下边框清晰且粗细一致。
- 宽屏/紧凑布局尺寸与迁移前一致。
- 抽屉裁剪范围无泄漏。

### HD-2：动态覆盖层高清化

迁移：

- 天体选择环、悬停环。
- 锁定红叉；停靠位置继续由飞船图标表达，已探访状态保留在详情文字中。
- 深空跃迁虚线、飞船箭头和系统内飞船图标。
- 跃迁进度条。

`StarMapCanvas` 继续保持独立，不改天体贴图生成和缓存策略。

验收：

- 所有覆盖层仍与天体中心对齐。
- GUI Scale 改变后无半像素漂移。
- 跃迁期间悬停和点击锁定行为不变。

### HD-3：按钮视觉与输入兼容

保留 Minecraft `Button` 作为：

- 点击框。
- 键盘焦点。
- 旁白入口。
- active/visible 状态容器。

仅将 `SciFiButton.renderWidget` 的背景、边框和状态高亮迁移到高密度绘制器。
按钮文字先继续由 Minecraft 原生字体绘制。

验收：

- 鼠标、键盘、旁白行为无变化。
- 禁用原因悬停提示仍可触发。
- 紧凑抽屉的关闭按钮和跃迁按钮层级正确。

### HD-4：拆分 Screen 渲染职责

在前述视觉效果稳定后，将 `ShipConsoleScreen` 中纯绘制逻辑逐步移动到：

- `StarmapChromeRenderer`：框架与通用装饰。
- `StarmapOverlayRenderer`：选择、飞船、航线等动态覆盖层。
- `StarmapDetailRenderer`：现有详情文字排版。

`ShipConsoleScreen` 继续拥有页面状态、选择状态、控件注册和跃迁命令。此阶段是代码
结构重构，不同时改变视觉设计。

验收：

- 每次抽取前后截图一致。
- `ShipConsoleScreen` 不再直接包含大量通用图元辅助函数。
- 页面状态恢复和抽屉逻辑测试不回退。

### HD-5：字体可行性门槛（单独决定）

这是高密度 UI 中风险最高、但并非基础层必需的部分。候选方案：

1. 保持 Minecraft 原生字体：兼容最好，清晰度提升有限。
2. 增加许可明确的高清中文字体资源：细节最好，但包体、字库覆盖和许可成本高。
3. 仅对数字、标题和图标使用高清字体，正文保留原生字体：折中方案。

推荐先采用方案 1 完成 HD-0～HD-4，再通过实机截图判断是否真的需要方案 3。
在字体决策前，不开始复杂二级详情菜单。

### 后续：二级详情菜单

只有 HD-0～HD-4 验收通过，且字体方案明确后，才重新设计行星详情信息卡。届时它
作为高密度基础层的使用者，而不是与基础设施改造混在同一次提交中。

## 7. 验证矩阵

至少覆盖：

| 窗口/显示场景 | GUI Scale | 关注点 |
|---|---:|---|
| 1280×720 或同等级窗口 | 2、3 | 宽屏布局、文字空间、点击区域 |
| 1920×1080 | 3、4 | 高 GUI Scale 下的线条与边框 |
| 2560×1440 或更高 | 4、Auto | 物理像素利用率、纹理尺寸和性能 |
| 低逻辑分辨率紧凑布局 | 3、4 | 抽屉裁剪、关闭按钮、地图可见区域 |

每阶段自动检查：

- `git diff --check`
- `gradlew test`
- 坐标正反投影与密度转换单元测试。
- 布局区域不越界测试。

每阶段实机检查：

- 星域、恒星系、行星聚焦三页。
- 宽屏详情面板与紧凑抽屉。
- 选择、悬停、右键返回、按钮禁用提示。
- 跃迁开始、自动切页、到达与中途重开星图。

## 8. 性能与资源预算

- HD-0～HD-4 主要增加矩阵变换和少量顶点，不新建全屏 RenderTarget。
- `StarMapCanvas` 仍是主要纹理开销，继续遵守 2048 最大尺寸与 LRU 缓存限制。
- 静态框架不生成每帧新纹理。
- 若后续采用全屏 RenderTarget，必须另做显存预算和窗口重建测试，不自动纳入本计划。

## 9. 回退策略

- `StarmapUiDensity` 必须支持强制 `D=1`。
- 每阶段都以独立提交交付，不跨阶段混合布局或交互改动。
- 高清渲染器失效时回退现有 `GuiGraphics` 路径，而不是关闭整个星图。
- 不删除现有响应式布局测试，迁移后继续作为兼容基线。

## 10. 实施前待确认事项

1. 是否批准推荐的方案 B：渐进式 2× 混合层，而不是整套 UI 重写？
2. 是否同意第一轮只高清化几何与控件外观，文字保持 Minecraft 原生字体？
3. 是否同意保留现有响应式布局尺寸，只提高绘制密度，不借机重新排版？
4. 是否同意先完成 HD-0 对比原型，实机证明有效后才继续 HD-1？

推荐答案均为“同意”。这样能最早验证核心假设，并把每一步的回归范围限制在可控程度。

## 11. 决策记录

2026-08-22，批准采用方案 B，并确认以下实施基线：

- 使用渐进式 2× 混合层，不整套重写星图 UI。
- 第一轮只提高几何、图标和控件外观的绘制密度，文字保持 Minecraft 原生字体。
- 保留现有响应式布局尺寸，不在高密度基础改造中同时重新排版。
- 严格从 HD-0 对比原型开始；实机确认有效后才进入 HD-1。

2026-08-23，HD-0～HD-4 已逐阶段完成自动检查、实机验收和远端推送：

- `6d4395c`：验证 2× 高密度绘制方案。
- `363e834`：高清化静态框架。
- `684c547`：高清化动态覆盖层。
- `7b2355e`：高清化按钮外观并保留原生输入行为。

HD-5 最终选择方案 1：继续使用 Minecraft 原生字体。当前没有引入自定义中文字库；
若后续美术原型证明标题、数字或图标确有更高字体密度需求，再单独评估局部字体方案，
不阻塞星图美术风格优化。至此，本高密度基础计划关闭，后续视觉设计作为独立任务推进。
