# 舰载人工智能终端与序章剧情计划

> 状态：T0 独立原型已通过视觉验收；P0 权威剧情数据、P2.1 环境状态门禁与 P4.2 矿物扫描剧情已接入，P2.2 环境演出待实现
>
> 目标版本：Minecraft 1.21.1 / NeoForge 21.1.x / LDLib2 2.2.36.a
>
> 建立日期：2026-08-29
>
> 当前优先级：验证 P4.2 矿物扫描节奏；钻石任务、亚光速引擎点火、飞船灯光与设备屏幕演出仍待确认或实现。

## 文档目的

新增一个有水平方向的“舰载人工智能终端”方块，并让它成为模组序章、主线任务、教程提示和飞船
状态叙事的统一入口。终端的核心不是自由聊天，而是由舰载 AI 通过对话推进实际游戏内容。

本文只记录已确认需求、建议方案、实现阶段和待讨论问题。尚未确认的剧情和玩法不得在实现时自行
补全。

## 当前首版实现边界

首版目标是先证明“舰载 AI 终端本身”在游戏中好看、易读、可交互，并建立后续剧情可以复用的稳定
界面骨架。当前只实现：

- 可放置、可破坏、具有四向水平朝向的 AI 终端方块及其物品；
- 无物品槽位的菜单边界，以及基于项目 `StarboundModularScreen` 的 LDLib2 页面；
- 左侧诺瓦投影区域、右侧流式对话记录、底部回答选项和必要的状态提示；
- 一组与世界进度无关的本地演示对话，用于验证流式输出、跳过、滚动、选项切换和关闭重开；
- 独立 LSS 视觉语言、中英文与常用 GUI Scale 适配。

T0 原型阶段明确不实现的共享剧情存档、任务推进、聊天栏广播、飞船灯光联动和真实服务端剧情动作，
已在后续 P0/P2.1/P4.1 中按阶段接入；飞船灯光、设备屏幕外观和引擎维修仍未完成。演示数据
必须与最终剧情模型解耦，不能把临时文本或客户端状态写成最终主线逻辑。

## 已确认决策

- 舰载 AI 名称为 **N.O.V.A.（诺瓦）**，全称为 **Navigation, Operations & Vessel Assistant**。
- 诺瓦采用冷静、可靠、无明显性别倾向的合成智能投影；保留便于交流的类人轮廓，但减少真实人类
  的面部、皮肤和发型特征，明确表现为非实体人工智能。初期表达偏系统化，随剧情推进逐渐表现出
  更自然的人格、幽默和对玩家的关心。
- AI 终端是可破坏、可重新放置的四向方块，放置时屏幕正面朝向玩家。
- AI 终端提供简单配方，玩家丢失终端后可以重新制作；具体材料仍待确定。
- 主线和飞船设备状态由世界或飞船共享，不能按玩家分别保存。
- 玩家是否见过对话、是否接收过教程等认知状态按玩家独立保存。
- 第一条主线为“找到 AI 终端并重启系统 → 了解事故 → 使用传送器前往行星表面”。
- 第一阶段不制作独立任务日志，也不接入真实大语言模型；对话采用本地化的剧情节点和回答选项。
- 诺瓦可以通过玩家左下角聊天栏进行远程广播，例如呼叫玩家寻找终端，以及在行星表面提示物质枪
  的使用方法。
- “跃迁引擎损坏”在引擎维修玩法实现前只作为剧情状态，不提前发布无法完成的维修任务。
- 故障期间只有星图导航台和飞船传送器被剧情锁定；打开后只显示一个不可操作的 `FATAL ERROR`
  弹窗，不附带故障代码、原因或其他详细说明。
- 燃料控制器保持可访问。物质枪升级工作台和合金炉是否出现在初始飞船中尚未确定，因此暂不纳入
  序章故障状态设计。
- 不再向新玩家直接赠送可放置传送器物品，避免绕过飞船传送器和序章任务。
- “重启核心系统”采用一次点击后由服务端持续约 2–3 秒的共享过程；关闭 UI 不会中断重启。
- 故障期间保留暗红色应急照明，不使用完全黑暗或青色应急灯。
- 诺瓦在 UI 左侧以肩部以上的像素艺术投影出现：正常状态使用青白色，采用清晰的原生像素轮廓和
  受控色板，不把普通插画经过滤镜伪装成像素画，也不采用普通 NPC 式造型。
- 诺瓦通过几何化眼部或面罩光带、头部角度和投影稳定度表达状态；故障时像素轮廓断裂并局部错位，
  恢复时从中央向上下重建完整轮廓。
- 首版人物素材暂定采用“复古像素合成智能”造型：分段式几何头部外壳、深色无面孔面罩、断续青色
  眼部光带、模块化颈肩结构，下部逐渐分解为像素列和投影碎片。该造型作为原型基线，视觉验收后
  仍可调整，不提前锁定为最终角色设定。
- 诺瓦不使用“船长”“乘员”等固定身份称呼；优先使用玩家名称，不适合插入名称的句子直接使用
  模糊的“你”。
- 初次状况总结中的四个信息主题都必须阅读，但玩家可以自由决定顺序；全部读完后才解锁推进任务的
  “我接下来应该做什么？”选项。
- 宇宙风暴使飞船脱离原航线；幸运的是，失控飞船最终漂入一颗郁郁葱葱的翠绿星球轨道。该星球
  在玩法上对应 Minecraft 主世界维度。
- 飞船仍可居住并能恢复核心供电，但推进系统完全离线，无法主动离轨或继续航行；重启诺瓦不会
  同时修复动力。
- “失去动力”是序章起始状态，而不是对现有核心玩法的永久取消。项目现有主循环包含共享燃料、
  星图选择、同星系/跨星系跃迁和抵达其他天体；后续剧情必须为这些能力提供恢复或重新解锁路径。
- 动力恢复明确分为两个先后阶段：先修复**亚光速引擎**，恢复恒星系内航行；再修复
  **超空间引擎**，恢复跨恒星系航行。
- 核心系统重启后，星图恢复打开和浏览功能，但所有航行操作仍因引擎离线而锁定；玩家可以查看
  当前恒星系，提前了解附近的天体和维修引擎的意义。
- 亚光速引擎修复后开放当前恒星系内航行；第二恒星系此时只显示为未知目标或不完整信号，不能
  选择其中的天体，也不能发起跨星系跃迁。
- 超空间引擎修复后恢复完整深空星域信息，显示并开放第二恒星系及其跨星系航线。

## 设定调整与现有功能衔接原则

- 当前代码和 README 是已经实现的**功能资产清单**，不是不可修改的剧情设定。新序章可以调整
  “母星”、初始流程、设备赠送方式、飞船事故和引擎状态等设定；方案确认后再同步更新 README。
- 剧情调整不能遗忘或无意移除已经实现的共享燃料、燃料控制器、三级星图、同星系/跨星系跃迁、
  两个恒星系、四个可达天体、传送网络，以及物质枪与升级系统。
- 每一项现有功能都必须明确属于“序章即可使用”“暂时锁定后解锁”“通过后续任务恢复”或
  “有迁移方案的重写”之一，不能留下永久死路，也不能只在文案中锁定而让服务端操作仍可绕过。
- “引擎损坏、飞船失去动力”按已确认剧情保留；在维修玩法确定前，不擅自解释成单纯燃料耗尽。
- 新旧设定发生冲突时，先决定现有功能在新剧情中的入口和状态迁移，再修改代码、README 与其他
  玩家文档，确保实现、剧情和说明同步。

### 动力系统与现有跃迁功能的对应关系

- 亚光速引擎对应已经实现的同恒星系天体间航行。完成第一阶段维修后，玩家可以在当前恒星系内
  选择并前往其他天体，但仍不能沿超空间航道前往另一个恒星系。
- 超空间引擎对应已经实现的跨恒星系航行。只有完成第二阶段维修后，跨星系航线才恢复可用。
- 引擎维修状态负责决定航线是否可用，共享燃料负责判断已开放航线能否实际启程；两套系统不能
  互相替代。拥有足够燃料不会绕过损坏的引擎，修好引擎也不会免除航行燃料消耗。
- 现有同星系 20 燃料、跨星系 100 燃料的规则暂作为功能基线保留；若后续进行数值平衡，应单独
  讨论并同步修改实现与文档。

### 星图的分阶段开放

1. `CORE_ONLINE`：星图不再显示 `FATAL ERROR`，允许浏览当前恒星系；所有跃迁按钮由服务端保持
   禁用，并明确提示亚光速引擎离线。
2. `SUBLIGHT_ENGINE_ONLINE`：开放当前恒星系内的天体选择和航行；深空星域中的第二恒星系以未知
   目标或不完整信号呈现，不暴露其完整天体信息。
3. `HYPERDRIVE_ONLINE`：恢复完整深空星域、第二恒星系信息和跨星系航线，现有两级跃迁功能全部
   可用。

该限制必须同时作用于星图表现、按钮状态和服务端航行校验。未知恒星系并非删除现有内容，而是把
已经实现的第二恒星系作为超空间引擎修复后的明确探索奖励。

## 核心体验目标

序章不能只是打开 UI 阅读一段文字。玩家重启诺瓦时，飞船应从“严重故障”进入“应急系统恢复”状态，
并通过灯光、设备屏幕、聊天广播和 AI 形象变化共同表现。

体验顺序应为：

1. 玩家在昏暗、部分设备故障的飞船中醒来。
2. 左下角收到残缺但可辨认的诺瓦广播。
3. 玩家主动寻找并操作 AI 终端。
4. 玩家执行一次明确的系统重启操作。
5. 诺瓦的形象由故障噪声逐步恢复，终端输出启动日志。
6. 飞船灯光和现有控制设备的显示屏恢复正常。
7. 诺瓦总结事故与当前状态，并通过选项回答玩家的问题。
8. 诺瓦发布“初次登陆”任务，引导玩家使用传送器前往行星表面。
9. 玩家抵达行星表面后先确认通讯链路，约 6 秒后收到探索与物质枪教程广播，主线进入下一阶段。

系统重启过程应短促明确，不能成为拖沓的不可跳过演出；不接管相机，也不限制玩家关闭界面。

## 序章剧情草案

### 阶段 0：异常苏醒

首次进入世界的玩家生成在飞船上。数秒后，聊天栏显示：

> **[N.O.V.A.]** 警告：检测到严重系统故障。核▒心状▓态：#%/无法读取。请重启核心系统。

若玩家一段合理时间内没有与终端交互，可以再发送一次定位提示，但不得循环刷屏：

> **[N.O.V.A.]** 通信链路不稳定……请前往舰载人工智能终端，重启核心系统。

此时飞船处于应急状态：

- 主照明关闭或显著变暗，只保留暗红色应急灯提供必要可见度；
- AI 终端显示故障纹理或不稳定画面；
- 星图导航台与飞船传送器被锁定；玩家打开后只看到一个写有 `FATAL ERROR` 的不可操作弹窗，
  不显示诊断说明，也不能进入星图、选择目的地或执行传送；
- 燃料控制器保持可访问。其当前功能更接近独立油箱，不作为核心系统故障演出的对象；
- 飞船门和储物柜保持可用，避免困住玩家或阻止取用物品；
- 物质枪升级工作台与合金炉暂不定义故障状态。默认飞船结构和初始设备清单确认后再决定它们是否
  随核心系统下线。

### 阶段 1：重启诺瓦

玩家首次打开终端时，不立即进入普通对话，而是看到故障界面：

- 左侧 AI 形象区只有轮廓、噪声和断续信号；
- 右侧显示少量诊断信息；
- 页面只有一个明确主操作：**重启核心系统**。

玩家主动点击该按钮，而不是右键方块后自动完成重启，以保留参与感。重启请求必须由服务端确认，
并以原子方式改变共享飞船状态，防止多人同时触发两次。流程持续约 2–3 秒；玩家关闭 UI 后，
服务端仍继续完成重启。若服务器在过程中关闭，下次启动时直接完成恢复，不能永久卡在中间态。

建议启动日志：

> 核心系统重启中................
>
> 核心供电恢复中……
>
> 航行数据索引重建失败
>
> 人工智能人格矩阵恢复中……
>
> N.O.V.A. 核心已上线

日志采用短句流式输出，玩家可单击跳过文字动画并立即显示完整内容。

### 阶段 2：飞船恢复

诺瓦上线时触发一次可见的飞船环境变化：

1. 应急灯或终端指示灯短暂闪烁；
2. 主照明分段亮起；
3. AI 终端由故障画面切换为正常界面；
4. 星图导航台恢复浏览功能但仍禁止航行，传送器解除 `FATAL ERROR` 锁定；
5. 诺瓦发出一条恢复广播。

> **[N.O.V.A.]** 核心系统已恢复。我正在评估飞船的整体状态。

AI 页面应保持紧凑且不使用全屏黑色遮罩，让玩家仍能看到 UI 周围的世界和设备变化。恢复过程只
更新当前仍存在的设备，不得重新放置玩家已经拆除的方块，避免破坏玩家自定义飞船。

当前程序化飞船使用永久发光的海晶灯，不能直接表现上述过程。实现时需要新增可切换亮灭状态的
舰灯，或采用等价的受控照明方案；不能只播放 UI 动画冒充飞船恢复。

当前程序化飞船的整体结构也尚未被视为最终方案。AI 终端的位置、升级工作台和合金炉是否作为
初始设备赠送，都要等默认飞船结构确认后再决定；序章系统不得反过来把临时布局固化成最终设计。

### 阶段 3：状况总结

诺瓦恢复后开始总结。需要称呼玩家时优先使用玩家名称，其他句子直接使用“你”，不预设玩家是
“船长”或“乘员”：

> **N.O.V.A.：** 舰载系统已恢复。你的生命体征稳定。很高兴再次与你取得联系。
>
> **N.O.V.A.：** 飞船遭遇了一场高强度宇宙风暴，随后偏离原定航线。部分导航数据在事故中丢失，
> 我仍在分析具体原因。
>
> **N.O.V.A.：** 定位已经完成。幸运的是，我们目前位于一颗宜居星球的轨道上。初步扫描表明地表环境适合活动，
> 尚未发现会立即威胁生命的因素。
>
> **N.O.V.A.：** 推进系统已经离线，飞船暂时无法依靠自身动力离开轨道。传送系统仍可使用；
> 建议优先恢复亚光速引擎。

玩家先看到四个必要状况问询，可以自由选择阅读顺序：

- `你是谁？`
- `发生了什么？`
- `我们现在在哪里？`
- `飞船还能航行吗？`

四项全部读完后才解锁：

- `我接下来应该做什么？`

选项只负责选择剧情分支，不伪装成可理解任意语言的输入框。已经询问过的主题保留明确完成标记并
允许重新查看，不能只靠轻微颜色差异表达；任务推进选项在条件未满足时不执行。玩家可随时关闭 UI，
重新打开后继续当前节点，已读状态按玩家保存，也不重复执行系统重启。单击跳过流式动画并完整显示
当前回答后，同样视为已经阅读。

### 阶段 4：初次登陆

诺瓦最终给出建议：

> **N.O.V.A.：** 传送器运行正常。抵达地表后，我会重新建立通信链路并继续分析周边环境。
> 现阶段建议先探索地表，使用物质枪收集基础资源。

随后记录共享主线目标：

> **新任务：初次登陆**
>
> 通过飞船传送器前往星球表面。

完成条件必须是玩家实际通过传送链路抵达行星表面，不能通过客户端按钮直接标记完成。

### 阶段 5：行星表面教程

玩家完成第一次地表传送时，诺瓦先通过聊天栏确认抵达：

> **[N.O.V.A.]** 已确认你抵达星球表面，通信链路现已恢复。

约 6 秒后，再向尚未看过教程的玩家发送探索建议，让玩家先观察落点：

> **[N.O.V.A.]** 建议先探索附近区域，并使用物质枪收集基础资源。按住右键即可启动采矿激光。

玩家完成初次登陆并第一次拾取原木时，再发送一次资源反馈：

> **[N.O.V.A.]** 很好，你已经获得了木材。这是一种用途广泛的基础资源。根据当前数据，
> 你的生存概率提高了 17 个百分点。

仅当最终默认飞船确定包含升级工作台时，才在序章补充：

> **[N.O.V.A.]** 部分高强度材料需要更高的采矿等级。你可以在飞船上的升级工作台强化物质枪。

若升级工作台不属于初始设备，则把这条提示推迟到玩家首次获得或放置升级工作台之后。教程只对
尚未看过的玩家发送一次；终端保持主线入口定位，不再长期提供重复教程按钮。

### 阶段 6：轨道矿物扫描

玩家首次拾取原木后，诺瓦不立刻连续刷出信息，而是在木材反馈后留出约 15 秒，让玩家继续探索。
随后按 5 秒、6 秒间隔播放三段共享剧情广播：

> **[N.O.V.A.]** 轨道扫描设备已启动。地层矿物扫描中................
>
> **[N.O.V.A.]** 初步扫描已经完成。浅层地层中分布着煤、铜和铁；更深处还检测到青金石、红石，
> 以及少量钻石。
>
> **[N.O.V.A.]** 钻石的晶体结构或许可以替代亚光速引擎点火阵列中损坏的聚焦晶体。我还需要核对
> 完整的修复方案。在此之前，请继续收集基础资源。

扫描只报告矿物类型和大致地层，不遍历区块、不提供矿脉坐标，避免运行开销和过度削弱探索。
过程保存为共享飞船状态，只由第一名符合条件的玩家触发一次；服务器重启会从已保存阶段继续，
每次只推进一段消息。晚加入玩家不重新播放演出，可在 AI 终端当前状态摘要中查看扫描结果。

### 后续候选：亚光速引擎点火（尚未实现）

钻石在后续剧情中不是引擎燃料，而是用于修复聚变点火阵列的高压聚焦晶体。以下内容只保留为
后续提案，本轮矿物扫描不会创建钻石任务、扣除物品或改变引擎状态：

初始物质枪的采矿等级只能稳定获取铁矿及以下矿物，无法正确掉落钻石。矿物扫描完成后，诺瓦应
明确提醒玩家先提升采矿等级。物质枪组件采用序章可完成的十字配方：上、下、左、右各 1 个铁锭，
中间 1 个青金石，一次合成 2 个组件；两种矿物都能由初始物质枪获取。玩家返回程序化初始飞船，
将物质枪放入升级工作台并消耗 1 个组件，把采矿等级从 0 提升到 1，剩余组件可保留给其他升级。
该流程不再依赖尚未自然生成的钛、耐钢和星核材料，也自然引导玩家使用现有升级系统。

建议将任务分成两个清晰步骤，避免玩家拿着低等级物质枪直接寻找钻石：先显示“制造物质枪组件，
将采矿等级提升至 1”，服务端确认玩家持有的物质枪已经完成升级后，再切换为“取得 3 颗钻石”。
程序化初始飞船当前确实放置了升级工作台；若最终飞船结构移除它，必须同时为工作台提供可达的
早期配方或其他明确入口，不能让主线依赖一个不存在的设备。

完成校准后，个人目标更新为“取得 3 颗钻石”。服务端以玩家实际持有的钻石数量判断是否可提交，
不依赖容易漏掉的“挖掘方块”事件，因此战利品箱、交易或队友交付也能正常推进。建议玩家回到 AI
终端提交材料：终端显示 `点火晶体 0/3`，数量不足时按钮禁用并说明原因；提交时服务端原子地扣除
3 颗钻石，避免多人同时提交造成重复消耗。

提交后播放约 3 秒的短点火序列：诺瓦报告“聚焦阵列校准”“反应室点火”“亚光速引擎上线”，
飞船尾部或工程区由暗红应急状态切换为稳定灯光，随后共享的亚光速引擎状态变为 `ONLINE`。星图
立即开放当前恒星系内航行，但仍保留燃料消耗；超空间引擎继续损坏，第二恒星系仍只显示未知信号。
晚加入玩家直接获得当前共享阶段摘要，不重新触发扫描、材料扣除或点火演出。

该方案仍需确认三项决定：钻石数量是否采用 3 颗；升级工作台是否固定保留为初始飞船的必要设备；
钻石是否直接在 AI 终端提交，还是等后续新增实体引擎控制台后再提交。

## 共享进度与多人规则

### 飞船共享状态

以下内容属于真实世界状态，由所有玩家共享：

- 当前主线章节；
- 诺瓦核心是否恢复；
- 飞船照明与设备在线状态；
- 亚光速引擎是否损坏或修复；
- 超空间引擎是否损坏或修复；
- 传送器、导航等系统是否解锁；
- 当前停靠位置和已经完成的飞船任务。
- 当前星球的轨道矿物扫描阶段与完成状态。
- 当前轨道目标为翠绿天体，其可探索表面在技术上复用 Minecraft 主世界维度。

首个阶段可按世界保存；未来支持多艘独立飞船时，再迁移为按飞船 ID 保存。

### 玩家个人状态

以下内容按玩家保存：

- 是否与诺瓦完成个人身份确认；
- 已阅读的必要状况主题，以及是否已经解锁任务推进选项；
- 已收到的物质枪和其他操作教程；
- 是否关闭某类可选提示。

### 晚加入玩家

若一名玩家加入时其他船员已经恢复诺瓦或修好设备，该玩家不得看到过时的世界状态，也不得重新
触发共享演出。诺瓦应提供符合当前飞船状态的简短说明，例如：

> **N.O.V.A.：** `<玩家名称>`，核心系统已经恢复。我可以为你整理当前状况与可执行任务。

共享状态优先于个人对话节点。个人剧情落后时，通过摘要和身份确认追上当前章节，而不是把飞船
倒退到旧状态。

## AI 终端方块

- 暂定注册名称：`ship_ai_terminal`；最终中英文显示名仍可调整。
- 使用水平四向 `FACING`，屏幕朝向放置者。
- 可正常破坏、拾取和重新放置。
- 提供简单配方；配方应在序章阶段可发现，防止终端丢失后无法继续剧情。
- 方块本身不保存主线进度。破坏、移动或重新合成终端不会重置诺瓦与飞船状态。
- 新放置的终端根据共享飞船状态直接显示故障或在线外观。
- 终端可以包含方块实体以保存终端本地信息，但不得把世界主线唯一地锁在某一个方块实体内。

## LDLib2 界面方案

界面采用横向紧凑终端，不沿用星图的全屏视觉，也不照搬传送器页面。建议结构：

```text
┌──────────────────────────────────────────────────────┐
│ N.O.V.A. 舰载人工智能                    核心状态     │
├──────────────────┬───────────────────────────────────┤
│                  │ 流式启动日志 / 对话历史           │
│   AI 形象区      │                                   │
│                  │                                   │
│   当前表情状态   │ 回答选项或唯一主操作               │
└──────────────────┴───────────────────────────────────┘
```

- 左侧约占 35%，显示诺瓦的合成智能投影和待机、故障、恢复、思考、说话、警告状态。
- 投影采用肩部以上构图和青白主色；不绘制真实鼻、嘴、皮肤、头发或普通服装，以眼部光带、
  头部角度和信号稳定度表达情绪，避免写实人像或普通 NPC 感。
- 故障状态使用轮廓断裂与局部错位；系统恢复时从投影中央向上下重建轮廓，不使用拖沓的全屏演出。
- 右侧约占 65%，使用裁切正确的 `ScrollerView` 展示启动日志和对话历史。
- 对话文本按短句或字符流式更新，但保持稳定元素树，不在每次输出时重建整个页面。
- 玩家查看旧消息时暂停自动跟随，并提供“回到最新消息”。
- 流式输出期间单击正文可立即完成当前段落。
- 回答选项使用明确按钮，不使用没有真实语义解析能力的自由文本框。
- 必要状况主题允许任意阅读顺序，已读项显示明显完成标记并可重新查看；全部读完前，推进任务的
  选项保持不可执行，全部完成后再明确解锁。
- 不给每段正文套边框，使用字号、颜色、缩进和间距建立玩家、AI、系统日志和任务提示的层级。
- 关闭、重新打开、窗口缩放和常用 GUI Scale 下必须保持当前剧情节点和正确滚动位置。

## 飞船环境联动

环境联动是序章的必要组成部分，应作为独立系统实现和验证：

- 新增可切换亮灭的飞船照明，替代或包装当前程序化飞船中的常亮海晶灯；故障状态使用暗红色
  应急灯，恢复后切换到正常主照明；
- 为新星图导航台和 AI 终端准备离线/在线显示屏外观，并为飞船传送器提供故障锁定状态；
- 星图导航台和传送器在故障状态下只能显示一个不含详细说明、不可操作的 `FATAL ERROR` 弹窗；
  锁定必须由服务端状态决定，不能仅在客户端隐藏按钮；
- 燃料控制器保持可访问，不纳入本轮环境恢复演出；
- 升级工作台和合金炉是否参与故障状态，等默认飞船与初始设备清单确定后再讨论；
- 系统重启只改变已存在且属于飞船系统的设备状态，不复原被玩家拆除的设备；
- 玩家后来放置的新设备应读取当前共享状态，而不是永远从故障外观开始；
- 旧 `ship_console` 已废弃，只为存档兼容保留，不应重新成为新飞船序章的依赖；
- 环境变化应在服务端变更状态并同步给所有附近玩家，不能只在触发者客户端播放假象；
- 可添加原创、低音量的系统重启提示音，但不得重新引入来源不明或有版权风险的音频素材。

## 建议的数据状态

共享飞船状态可先采用有限状态机，具体命名在实现时确定：

```text
EMERGENCY_OFFLINE
  -> CORE_REBOOTING
  -> CORE_ONLINE
  -> SURFACE_MISSION_ACTIVE
  -> FIRST_LANDING_COMPLETE
  -> SUBLIGHT_ENGINE_ONLINE
  -> HYPERDRIVE_ONLINE
```

状态变化必须单向、可保存、可在服务端验证并能在区块重新加载后恢复正确外观。进入
`CORE_REBOOTING` 后，即使触发者关闭 UI，服务端也继续运行约 2–3 秒的重启流程；若服务器在过程中
关闭，下次启动时直接迁移到 `CORE_ONLINE`，避免世界永久卡在启动中间态。
